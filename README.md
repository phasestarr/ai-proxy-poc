# AI Proxy

Internal AI proxy stack behind sibling `root-proxy`.

## Runtime

- Public entrypoint: `root-proxy`
- Public host: `ai.example.com`
- Edge upstream: `ai-proxy:8080` on external Docker network `edge-net`
- Frontend: NGINX serving the SPA and proxying `/api/*` and `/health`
- Backend: Compose service `backend` with default container name `ai-proxy-api`
- State: PostgreSQL for auth, session, OAuth, conflict ticket, chat history, attachment metadata, and chat operation tokens; Redis for chat rate limits
- Model execution: Vertex AI, OpenAI, and Anthropic

## Active Scope

- guest login
- optional Microsoft login through backend-owned OAuth redirect flow
- `HttpOnly` `session_id` cookie auth
- protected streaming chat endpoint
- backend-owned chat history with persisted user/assistant messages and completed thinking/tool blocks
- Postgres-token-fenced single in-flight operation per chat history, with internal draft staging only during blank-page file upload validation
- Redis-backed minute and hourly chat rate limits
- public model catalog at `/api/v1/models`
- Vertex-backed public Gemini model variants
- OpenAI-backed public GPT model variants
- Anthropic-backed public Claude model variants
- optional provider-neutral tools exposed per model, including `web_search`, `retrieval`, `code_execution`, and `url_context`

## In Repo

- `frontend/`: Vite + React frontend packaged behind NGINX
- `backend/`: FastAPI backend source directory
- `deploy/`: container deployment files for this stack
- `docs/`: architecture, API, environment, maintenance, and query notes
- `secrets/`: server-local mounted secret files

## Runtime Entry Points

- All runtime, deploy, and verification flows are defined from `deploy/`.
- Shared base compose: `deploy/docker-compose.yml`
- Server runtime: `deploy/docker-compose.server.yml` with repo-root `.env`
- Local runtime: `deploy/docker-compose.local.yml` with repo-root `.env.local`
- The server and local flows differ only by the compose override and env file.

## Setup Flow

From a fresh checkout:

```bash
git clone <repo-url> ~/ai-proxy
cd ~/ai-proxy/deploy
sh deploy.sh
```

Then choose one runtime guide:

- Server: `deploy/README-SERVER.md`
- Local: `deploy/README-LOCAL.md`

Before starting containers, replace every `$your-...` placeholder in the selected
env file and place required secret files under `secrets/`.

## Required Server Values

For server deployment, `.env` must match sibling `root-proxy` routing:

```text
root-proxy route: ai.example.com -> ai-proxy:8080
AI_PROXY_CONTAINER_NAME=ai-proxy
```

Set these environment values before server startup:

- PostgreSQL database, user, and password
- `AUTH_DATA_ENCRYPTION_KEY` for encrypted auth/session data
- provider credentials for all exposed model providers: Vertex AI, OpenAI, and Anthropic
- `GOOGLE_APPLICATION_CREDENTIALS` and the mounted file under `secrets/` if Vertex is enabled
- Microsoft Entra client values if Microsoft login is enabled
- Microsoft redirect URI in Entra: `https://ai.example.com/api/v1/auth/callback/microsoft`
- `AUTH_COOKIE_SECURE=true`

## Local IDE Setup

This section is only for editor support, smoke checks, and code navigation.
Runtime and validation stay Docker-first.

Do not install local PostgreSQL or Redis. Use the Compose stack from `deploy/`.

Keep these disposable local helper artifacts only when you want fast IDE
resolution:

- `frontend/node_modules`: local frontend dependency tree for TypeScript, Vite, and `npm` checks
- `frontend/dist`: disposable output generated by `npm run build`
- `backend/.venv`: lightweight Python interpreter and packages for IDE resolution and compile checks
- `backend/ai_proxy_api.egg-info`: editable-install metadata generated by `pip install -e .` for `app...` import resolution

If those artifacts are missing and you intentionally want local IDE indexing,
recreate them with:

```powershell
cd backend
py -3.13 -m venv .venv
.venv\Scripts\python -m pip install --upgrade pip
.venv\Scripts\python -m pip install -r requirements.txt -e .
.venv\Scripts\python -m compileall app
cd ..\frontend
npm ci
npm run typecheck
npm run build
```

Do not use local dev servers, local PostgreSQL, local Redis, or ad hoc runtime
commands as validation gates. Use Docker Compose from `deploy/`.

## Notes

- This repo does not terminate TLS.
- Server deployment assumes sibling `root-proxy` is the only public entrypoint.
- Server deployment assumes `root-proxy` overwrites `X-Real-IP` and `X-Forwarded-*` headers before requests reach this stack.
- Compose uses required env interpolation, so missing env values fail before container startup.
- Optional blank env values must still be present in env files as blank assignments.
- Microsoft login remains optional until the Microsoft env vars are configured with real values.
- The frontend does not auto-select a model; clients must choose one from the backend catalog before sending chat.
- The frontend `New chat` action is local-only. A text-only first send creates the chat history at send time; a blank-page file upload uses an internal Postgres draft while validation/counting/storage runs, then promotes it to a visible chat history before returning success.
- Internal upload drafts use `CHAT_DRAFT_TTL_SECONDS` as a cleanup safety net; local validation, compaction, and attachment mutations use `CHAT_VALIDATING_OPERATION_TIMEOUT_SECONDS`; provider streaming uses `CHAT_PROVIDER_EVENT_IDLE_TIMEOUT_SECONDS` for next-event liveness and `CHAT_PROVIDER_MAX_RUNTIME_SECONDS` as the hard cap.
- Database schema is managed by Alembic migrations at backend startup.
- Guest users are keyed by raw IP address in `guest_identities`; local Docker usually reports the Docker bridge IP such as `172.18.0.1`.
- In server mode that raw IP is expected to be the sanitized remote address supplied by `root-proxy`.
- Backend-local chat rejects are audit-logged in PostgreSQL without polluting persisted chat transcripts.
